# grove:work

Read `../../references/discipline.md` and `../../references/planning.md` once.

## Prepare

1. Run `grove status`. Resolve the selected work IDs. If a selected unit shows claimed on another branch, do not start it; resume there or coordinate with its owner instead. For several units, run `grove batch <ids>`; inspect external blockers and the dependency order. If given a release, select its next eligible members and preserve its final acceptance obligations. Once in the worktree, acquire the selected set with `grove claim <ids>`.
2. Run `grove context --work <id> --phase plan` for each selected unit and inspect its code pointers. Required context omissions must be resolved before coding: raise the budget or fetch the named sources, keeping each relevant constraint available. Do not scan the entire knowledge tree.
3. Check the specification, current checkout, prerequisites, and existing plan. Resolve technical unknowns from evidence. Prepare or repair the plan per planning.md, including a shared plan for a combined implementation. Record and surface its execution decision header (approach, reason, delegation, runtime and reassessment condition), or the small-work Next equivalent. Choose agent coordination and durable execution separately, using inspected ownership and available harness capabilities. A `ready` result means required content is present, not that the plan is correct, current, or authorized. Human outcomes and constraints define the mandate; routine technical choices inside it need no additional approval.
4. Fix unresolved blocking questions and missing relationships before dependent implementation. Ask the human only when the answer requires their preference or changes the mandate; continue independent work meanwhile. A release playtest can remain pending while its members proceed.

## Execute and verify

Enter the implementation worktree per discipline.md before the first change. Set each unit active when its execution starts, with started/updated dates and Next. Run lint. If scope grows beyond the recorded size, resize, update the plan and checks, and continue within authority; propose changes to outcomes or constraints before relying on them. A resize into bounded or large moves execution into the controller loop below, even if it started small.

Branch on the unit's recorded `size`.

**Small**: implement in-session as before. Single agent, run the existing suite, record evidence, proceed to close.

**Bounded or large**: run the controller loop. The lead prepares, dispatches, reviews reports and review files, and closes; it never writes code, runs tests, or debugs itself. Every dispatch uses the Agent tool as an ordinary subagent with an explicit `model`; do not rely on a phrase like "no teams" to keep it that way. On the run's first dispatch, verify what the tool actually returned (an agent id resumable with SendMessage) and record that in `.grove-run/ledger.md`; if the harness returns a teammate or no resumable handle instead, record the limitation in the work page's Evidence and continue with fresh dispatches rather than changing any setting. For each plan task, in dependency order, with attempt number N starting at 1:

1. Record the base revision: `git rev-parse HEAD`.
2. Write `.grove-run/<task>-brief.md` from `skills/work/implementer.md`: the task, the files/interfaces it touches, the acceptance line it serves, the discipline rules that apply, and the report format, naming this attempt's report path `.grove-run/<task>-a<N>-report.md`.
3. Dispatch a fresh implementer with the Agent tool, `model: sonnet`, prompt equal to the brief's path. It writes the full report to `.grove-run/<task>-a<N>-report.md` and returns only the compact lines (contract, attempt, outcome, tested revision, report path, one-line blocker if blocked or waiting) as its final message — no extra SendMessage announcing completion.
4. Write the diff to a file, never into the lead's context: `git diff <base> > .grove-run/<task>-a<N>-diff.patch`.
5. Dispatch a fresh task reviewer, `model: opus`, using `skills/work/reviewer.md` with the brief, report, and diff paths. It writes the full verdict to `.grove-run/<task>-a<N>-review.md` and returns the matching compact lines (contract, attempt, verdict, tested revision, report path).
6. Consume the attempt once: when the lead accepts it, append one line to `.grove-run/ledger.md` — task, dispatch, model, attempt id, report path, verdict or outcome, and tested revision. A later or repeated notification for an already-ledgered attempt (an idle notice, a duplicate completion) causes no redispatch, no reread, and no repeated handoff (see discipline.md). A return whose contract or attempt does not match the open dispatch, or whose report file is missing, is never accepted on the return alone: read the report path if it exists, otherwise resume the worker once with SendMessage asking for the report.
7. Fix loop, when the review has blocking findings: increment N. Rounds 1-3 resume the same implementer with SendMessage, attaching the findings; rounds 4-5 dispatch a fresh implementer on `model: opus`. Each round's scoped re-review of only the changed files resumes the same task reviewer with SendMessage, never a fresh one. Before dispatching the next attempt, reconcile or explicitly stop the previous attempt if it can still write files or owns a running test, and record that in the ledger. After round 5, stop, record the still-open findings, and report to the human instead of looping further.
8. Append the task's evidence line to the work page: models used per dispatch, fix rounds run, tested revision, and the command results the report carries.

A worker runs its checks in the foreground and collects exit status and output before reporting; if the harness leaves a command running, it keeps the handle and waits for the completion notification rather than finishing with a promise to wake later. A report that must hand off a still-running check says `outcome: waiting` and names the command, its owner (the worker), the evidence path it will write, and the wake condition. The lead then waits on that one worker through the harness's completion notification, resuming it with SendMessage if it goes idle without a report; it never polls an empty notification queue in a loop.

After the last task, write the whole-branch review brief. For a multi-component change, the lead adds a short affected-sequence list derived from the outcome and the changed interfaces (3-6 transitions, e.g. "dispatch → close and reopen the optional view → return → dispatch again", "damaged return → next dispatch", "label shown → actual completion semantics"). Dispatch one whole-branch review on the session model (name it explicitly in the dispatch); it maps each transition to existing evidence (a test, a report line, a screenshot with what it shows) and gives each uncovered transition an explicit disposition — mechanical defect found, missing evidence (naming the check to run), or reserved human judgment (leave the box unchecked, name it). Passing component checks never satisfy a transition by themselves; a screenshot's existence is not evidence of what it shows. Only for transitions the review marks missing evidence, dispatch one focused verification worker (`model: sonnet`) that runs those checks on the integrated revision and inspects the visible result when presentation changed, reusing existing evidence rather than rerunning it indiscriminately — no mandatory browser suite, no new framework. Allow at most one fix dispatch on `model: sonnet` for findings from the whole-branch review or its verification worker, then invoke `grove:close`.

Model rules, stated once: implementer dispatches use sonnet; reviewer and escalated-fix dispatches use opus; planning and the final whole-branch review use the session model. Every dispatch names its model explicitly. These are prose rules, not configuration: no frontmatter, no grove.toml entry.

`.grove-run/` is gitignored; it holds briefs, attempt-numbered reports (`<task>-a<N>-report.md`) and reviews (`<task>-a<N>-review.md`), diffs (`<task>-a<N>-diff.patch`), and the ledger for the run, kept out of the lead's context and off the branch.

The run checkpoint is the run's lines in `.grove-run/ledger.md` plus each selected work page's Next: selected work IDs and their order; the current task and attempt when one is open; completed tasks with their consumed attempt id, report path and tested revision (the ledger lines above); outstanding worker or command handles with their owner; pending human judgments as unchecked acceptance boxes with a reason; and the next action. Update it at task/work boundaries and before any wait or handoff. Never copy a full report into it; keep it short enough to reread on every resume.

Scale the checkpoint to the run: small single-agent work keeps it in the work page's Next and Evidence and needs no ledger. A batch without a release checkpoints each member's state separately in the same ledger; no umbrella is invented. Only when a release is in scope, activate its umbrella when the first authorized member starts (started/updated dates, Next) and track member progress against the release acceptance in the umbrella's Next; activation is not closure.

Record completed steps and evidence as work proceeds: command, result, tested revision or checkout, and acceptance it supports. Keep Next specific. To hand a prepared selection to an executor or a later session, run `grove export <ids> --out FILE`; it records source and checkout identity, acceptance and bounds, and refuses unprepared work. The executor returns a result document (contract id, work, outcome, tested revision, evidence, findings, next); `grove reconcile RESULT --contract FILE` writes it onto the work pages and refuses when any exported input changed. Acceptance boxes stay the agent's or human's judgment. Shared implementation retains per-unit acceptance and adds joint integration checks. Serialize shared writes; use separate workspaces for concurrent implementation only after inspecting ownership and interfaces.

On interruption, reread the checkpoint, then compare it with each selected work page's status and Next and any live agent handles before repeating a step or redispatching: small work reads `git status`/`git diff --stat` and inspects the partial diff directly, while a bounded or large unit instead reads `git status`/`git diff --stat` and `.grove-run/ledger.md` for the last ledgered attempt, not the diff itself. A completed task or consumed attempt already on the ledger is never redone. A late notification for an attempt already on the ledger does not reopen it; a return whose attempt identity is unrecorded or unmatched, or a worker gone idle without a report, is investigated per the controller loop above before anything is accepted. An outstanding attempt whose handle survived is resumed with SendMessage; if a process or session restart lost the handles, treat the attempt as interrupted, keep its partial files, collect whatever report or diff exists, and dispatch a new attempt with the next id only after recording the interruption in the ledger. Deferred human judgments stay unchecked across resume. Reconcile changed assumptions and invalidated checks. Never treat an agent exit or a checked task as proof of acceptance.

For small work, review the resulting diff against the specification and plan; bounded and large work get this from the loop's whole-branch review instead. Use a focused independent review where a consequential boundary warrants it. Confirm each acceptance condition with appropriate evidence. Human judgment uses the actual attributed response and its context; do not replace it with test output or invent it.

Check proven acceptance boxes, then invoke `grove:close` for each completed unit in dependency order. Keep a release open until its integration and human acceptance conditions hold. Report the next useful action and remaining wait explicitly.
